# GPT-5.5: проверка и объяснение терминов

Дата: 13.09.2026.

## Что значает B0 и почему 0,10–0,15 — это плохо по смыслу

`B0_RULE` (rule-based baseline, базовый метод на правилах) не использует LLM.
Он намеренно делает простую проекцию:

1. создаёт одного обобщённого актора `User` («пользователь»);
2. создаёт один Use Case (вариант использования) на весь проект;
3. ставит все ФТ в линейный основной сценарий в исходном порядке;
4. строит одну линейную Activity diagram (диаграмму активности).

Поэтому он легко достигает 100% формального покрытия: каждому ФТ присвоена
ссылка. Но он не понимает, что в предзаказе кафе есть разные роли,
цели, ошибки оплаты, отмены и альтернативные ветви. Поэтому 0,10–0,15 означает:
формат правильный, но смыслово это слабый граф.

`Actor` (актор) — не конкретный человек, а роль или внешняя система,
которая взаимодействует с проектируемой системой: например, клиент, бариста,
платёжный сервис. Абстрактный `User` у B0 склеивает эти разные роли.

`Use Case` (вариант использования) — это отдельная цель актора и сценарий
её достижения. В нашей схеме он содержит ID, название, цель, акторов, trigger
(триггер), предусловия, постусловия, основные шаги, альтернативы, ошибки,
ссылки на ФТ/НФТ, user stories (истории пользователя) и system stories
(системные истории).

## Что такое FULL и почему Use Cases генерируются каждый раз

`FULL` (full pipeline, полный пайплайн) — это исследуемый метод:

`SpecificationReq → нормализация → Use Case Agent → схемы и правила →
Critic → accept/repair/fail → Activity Diagram Agent для каждого UC → Mermaid →
сквозная трассировка → evaluator`.

Для каждого нового `SpecificationReq` нужен свой `UseCaseSet`, потому что цели,
роли и сценарии зависят от входа. Сохранённые прежние наборы — это артефакты
эксперимента и gold reference (эталон для оценки), а не готовый ответ для нового
запуска. Подставлять gold в генератор нельзя: это была бы утечка эталона.

На выходе `UseCaseSet` содержит список акторов, список детальных Use Cases и
карту покрытия каждого ФТ.

## Зачем нужен B1_ONESHOT

`B1_ONESHOT` (one-shot baseline, одновызовной базовый метод) получает тот же
`SpecificationReq` и за один API-вызов должен вернуть весь набор Use Cases, activity-
диаграмм и ссылок трассировки в одном JSON. После этого запускаются те же
детерминированные валидаторы, но нет критика и повторного исправления.

Он нужен не как часть конечного продукта, а как контрольное сравнение. Если
одна и та же модель на одном входе лучше работает внутри `FULL`, то разницу
можно связать с декомпозицией, проверкой и исправлением, а не с другой моделью.

## Почему ответ может обрезаться

`LLM_MAX_OUTPUT_TOKENS=8000` — наш начальный защитный лимит на размер одного
ответа, а не теоретически выведенное число. Он сдерживает стоимость, время и
ущерб от зациклившегося или слишком длинного ответа. Модели не давали команду
«обрезать смысл». API механически останавливает генерацию при достижении лимита;
об этом говорит `finish_reason=length`.

После API ответ идёт в parser (разборщик Pydantic-модели), а затем в
формальные валидаторы. Незавершённый JSON не передаётся дальше как
будто он корректен. На `SCALE-008` с 16 ФТ даже лимит 32 000 не спас one-shot.
Архитектурное решение — пакеты меньшего размера и сохранение после каждой диаграммы.

## Что значит слепой судья

`Blind judge` (слепой судья) видит входные требования и кандидат, но не видит
названия `B0`, `B1`, `FULL`, модель-генератор и провайдера. Это снижает риск
предвзятости к бренду или названию метода. Он всё ещё может ошибаться или
предпочитать стиль своего семейства моделей, поэтому нужны другие модели и люди.

## Детерминированный метод и детерминированные проверки — не одно и то же

`Deterministic` (детерминированный) означает: одинаковый вход и одинаковые
правила всегда дают одинаковый результат. В проекте есть два разных применения:

- `B0_RULE` — целиком детерминированный метод. Он нужен только как нижний
  ориентир и контроль. Его низкая смысловая оценка и есть доказательство,
  что одних правил для нашей задачи недостаточно;
- валидаторы внутри `FULL` — детерминированные правила после LLM-
  генерации. Они не заменяют смысловое рассуждение, а ловят проверяемые
  формальные ошибки.

Поэтому тезис защиты звучит так: «одних детерминированных инструментов
недостаточно для смысловой декомпозиции, но детерминированные проверки
нужны для контроля LLM».

## Что такое формальные валидаторы

Это обычные локальные Python-функции в
`src/traceable_spec/validators/__init__.py`. Никакого внешнего сайта, API или
ссылки для обращения к ним нет. Они проверяют:

- соответствие Pydantic/JSON Schema (схеме данных);
- уникальность и существование ID;
- ссылочную целостность между ФТ, UC, шагами, узлами и рёбрами;
- наличие initial/final nodes (начала/конца) и корректность концов рёбер;
- двустороннюю трассировку;
- покрытие требований и неподтверждённые элементы;
- превышение лимита исправлений.

`Безопасно принять` в этом контексте не означает кибербезопасность. Это означает,
что downstream-этапы (следующие этапы) не получат сломанную схему, висячую
ссылку или элемент без объяснимого источника. Формальный допуск не означает, что
смысл идеален; для этого есть критик, LLM-судья и эксперты.

## E2E, SCALE-003 и восемь непротрассированных рёбер

`E2E` (end-to-end, сквозной) означает, что весь путь от `SpecificationReq` до
итоговых артефактов завершён, а объединённый формальный gate (допуск) пройден.
`E2E=0` у B1 не означает «ничего не запустилось». Он создал 8 UC и 8 диаграмм,
но результат не прошёл финальные проверки.

`SCALE-003` — локальный ID третьего проекта в новом size-scaling benchmark
(тестовом наборе масштабируемости). Это проект «Предзаказ и самовывоз из
кафе» с 8 ФТ и 13 НФТ. Это не название модели и не шкала.

В B1 восемь рёбер — по одному в каждой из восьми диаграмм — не имели
`related_step_ids` (ссылок на шаги UC). Из 134 поддержанных activity-элементов трассированы
126, или 94,03%. Порог для activity-элементов заявлен как 100%: каждый узел и ребро
должны иметь источник в UC или быть явно помечены как unsupported
(неподтверждённые). Этот порог взят из DoD (критерия готовности) в плане НИР,
а не подобран после просмотра результа. Отдельно для обязательных элементов UC задан
порог не менее 95%.

## Блокирующая ошибка и ограниченное исправление

`Blocking issue` (блокирующая ошибка) — замечание валидатора или критика,
при котором артефакт нельзя передавать дальше как корректный. Это не
отдельный вызов. Граф собирает все такие `ValidationIssue` и меняет маршрут:

`passed → finalize`, `failed + attempts remain → repair`,
`failed + limit exhausted → controlled failure`.

По умолчанию разрешены две попытки исправления. Каждая попытка получает
все найденные дефекты за один проход. Даже если ошибок десять, это не означает
десять отдельных попыток. После каждого repair все проверки запускаются заново.
Если после двух попыток хотя бы одна блокирующая ошибка остаётся, результат
сохраняется со статусом controlled failure (контролируемая неудача) и отчётом,
а не скрывается и не запускает бесконечный цикл. Лимит защищает от неограниченного
расхода токенов, зацикливания и смыслового дрейфа.

## Что было с отклонёнными ответами DeepSeek-судьи

Раньше была дана неточная формулировка о четырёх ответах, отклонённых из-за
лимита доказательств. Фактически было пять невалидных ответов:

1. три превысили прежний лимит 12 `evidence_ids` — было 13, 21 и 30;
2. один имел неверно закрытый JSON-массив;
3. один вернул `limitations` строкой вместо списка.

В этом месте валидатор сработал правильно: отклонил формат, не соответствующий
схеме. Необоснованным был прежний лимит 12, поэтому он увеличен до 100. Также
добавлено безопасное преобразование одной строки в список и усилен prompt. Повторный
прогон дал 8/8 валидных оценок. Исходные ответы и история не удалены.

Незакрытый JSON не был обрезан: провайдер вернул `finish_reason=stop`. Это одна
синтаксическая ошибка генеративной модели: вместо `]}` она вернула `}}`.

## Выбор модели и параметров

В аккаунте доступны `gpt-5.5`, `gpt-5.5-2026-04-23`, `gpt-5.5-pro` и
`gpt-5.5-pro-2026-04-23`. Выбран `gpt-5.5-2026-04-23`, потому что точный снимок
воспроизводим, а alias `gpt-5.5` со временем может переехать на другую версию.
Pro-вариант для пилота не нужен: цель — та же GPT-5.5, которую предложил руководитель,
а не другая дорогая конфигурация.

В `.env.openai` установлены точный model ID, `reasoning_effort=medium` для будущей
генерации в FULL и начальный лимит 8000. Для судьи команда запуска одинаково
переопределила их на `low` и 6000 для B0/B1/FULL. Ранние пробы `medium + 2400`
для B1 и FULL истратили весь лимит на reasoning tokens и завершились
`finish_reason=length`. Эти два вызова сохранены как диагностика, но не считаются
оценками диаграмм.

1. Добавить пакетную декомпозицию требований для Use Case Agent.
2. Провести контрольный live resume-run: остановить обработку после нескольких

3. После этого запустить `gpt-5.5-2026-04-23` внутри B1 и FULL на
   репрезентативных G1–G4.
4. Сохранить raw outputs (сырые ответы), конфиги, токены, время и стоимость.
5. Оценить одни и те же анонимные кандидаты DeepSeek, GPT-5.5, Claude и двумя
   экспертами.

Сохранение после каждой activity-диаграммы уже реализовано: root graph
выполняет один UC за один проход вершины `run_next_activity`, увеличивает
`next_activity_index`, а SQLite checkpointer сохраняет состояние между
проходами. Автоматический тест подтверждает промежуточное состояние. Пакетная
декомпозиция требований ещё не реализована; смена LLM без неё не устранит риск
длинного ответа Use Case Agent на крупных проектах.
