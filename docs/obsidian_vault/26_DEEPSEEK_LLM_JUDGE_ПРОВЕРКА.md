# Проверка результатов с помощью DeepSeek

Дата эксперимента: 13.09.2026.

## Короткий ответ

Да, LLM (большую языковую модель) можно использовать для оценки полученных
Use Cases (вариантов использования) и Activity diagrams (диаграмм активности).
Но эта проверка дополняет, а не заменяет детерминированные валидаторы
(проверки по однозначным программным правилам).

Используются два независимых слоя:

1. **Formal gate (формальный допуск)** проверяет JSON Schema (схему данных),
   ссылки, структуру графа, трассировку и неподдержанные элементы.
2. **Blind LLM judge (слепой LLM-судья)** проверяет смысл: правильность акторов,
   границ Use Case, сценариев, ветвлений, соответствия требованиям и читаемость.

Результат считается сильным только тогда, когда он проходит оба слоя.

## Что именно сравнили

Один вход `SCALE-003` содержит 8 функциональных требований. Для всех методов
использован один и тот же вход. Каждый сохранённый результат дважды оценён
DeepSeek-судьёй. Судья не получал название метода, модели и провайдера.

| Метод | Что делает | Формальный E2E | LLM-судья | Основной вывод |
|---|---|---:|---:|---|
| `B0_RULE` | строит результат правилами без LLM | 100% | 0,100 | формат корректен, смысловая декомпозиция слабая |
| `B1_ONESHOT` | один прямой вызов DeepSeek | 0% | 0,775 | смысл выглядит хорошо, но остались формальные дефекты |
| `FULL` | генерация, критика, исправление и валидаторы | 100% | 0,781 | прошёл оба независимых слоя |

`B1_ONESHOT` получил высокую оценку LLM, однако Activity structural validity
(структурная корректность activity-диаграмм) равна 0%, а трассировка элементов
диаграмм — 94,0%. Валидатор нашёл восемь рёбер без ссылки на шаг UC и одно
нарушение обязательного порога 100% — девять блокирующих замечаний двух
классов. Следовательно, LLM-судья способен пропустить формальную ошибку. Именно
поэтому валидатор нужен даже при использовании сильной модели.

## Как понимать, какое значение лучше

LLM-score (смысловая оценка) нормирован на диапазон от 0 до 1:

- ближе к 1 — лучше смысловое покрытие и качество представления;
- ближе к 0 — хуже;
- значение не является вероятностью правильности;
- высокий score нельзя интерпретировать отдельно от формального E2E.

На пилотном кейсе `FULL` лучше не потому, что 0,781 заметно выше 0,775. Разница
всего 0,006 и на одном кейсе статистически ничего не доказывает. Проверенное
преимущество `FULL` — сочетание высокой смысловой оценки с прохождением
формального E2E.

## Рубрика LLM-судьи

Каждое свойство получает оценку от 1 до 5:

1. покрытие требований — вес 20%;
2. правильность акторов и границ Use Case — 15%;
3. полнота основного и альтернативных сценариев — 20%;
4. корректность ветвлений — 15%;
5. правдоподобие трассировки — 10%;
6. отсутствие неподтверждённых предположений — 10%;
7. читаемость диаграмм — 10%.

Взвешенная оценка преобразуется из шкалы 1–5 в шкалу 0–1. Несколько разных
диаграмм могут быть правильными: судья сравнивает не буквальное совпадение
Mermaid-кода, а сохранение акторов, целей, шагов, ветвлений и источников.

## Цена пилота

За весь диагностический цикл, включая неудачные ответы при настройке строгого
формата, масштабный stress-test (нагрузочный тест) и повторные оценки:

- 68 обращений к DeepSeek;
- 518 075 входных токенов, из них 218 108 попали в cache (кэш);
- 222 163 выходных токена;
- 740 238 входных и выходных токенов суммарно;
- консервативная оценка budget guard — около 0,422 доллара США;
- расчёт по официальному Sunday off-peak тарифу с учётом cache-hit — около
  0,179 доллара США.

Первая сумма намеренно завышена: локальный ограничитель считает весь input как
обычный некэшированный запрос по peak-тарифу. Обе суммы являются расчётом, а не
банковским счётом. Фактическое списание нужно проверять в кабинете провайдера.

## Исправление формулировки об отклонённых ответах судьи

В первом диагностическом прогоне были отклонены пять из восьми ответов. Три
ответа содержали 13, 21 и 30 `evidence_ids` при прежнем лимите 12; один
содержал неверно закрытый JSON-массив; ещё один вернул `limitations` строкой
вместо списка. Поэтому прежняя фраза о «четырёх ответах, отклонённых из-за
лимита доказательств» была неточной.

Строгий parser (разборщик) сработал правильно: он не позволил незаметно принять
ответ не по схеме. Необоснованно жёстким был именно лимит 12 ссылок. Он
увеличен до 100; однозначная строка `limitations` теперь преобразуется в
список; prompt явно требует проверить закрытие скобок. Повторный запуск дал
8/8 валидных оценок. Исходный прогон не удалён, а кандидаты и их оценки не
редактировались.

Неверно закрытый массив не был результатом обрезки: API сообщил
`finish_reason=stop`. Это единичная синтаксическая ошибка генеративной
модели, которую и должен останавливать строгий контракт.

## Что обнаружено на более крупном входе

На `SCALE-008` с 16 функциональными требованиями:

- `B1_ONESHOT` был обрезан даже при лимите 32 000 выходных токенов;
- `FULL` сформировал 12 Use Cases, но достиг локального лимита после 29 вызовов
  и 215 697 токенов;
- во время этого запуска частично готовые activity-диаграммы не сохранялись по
  одной внутри текущей вершины root graph (корневого графа).

Это означает, что простого увеличения лимита токенов недостаточно. После
диагностики root graph разделён на отдельные вызовы `run_next_activity`, и
теперь LangGraph создаёт checkpoint (контрольную точку) после каждой
завершённой диаграммы. Автоматический тест подтверждает наличие такого
состояния. Для средних и больших проектов ещё нужна пакетная обработка
требований и контрольный live resume-run.

## Как будет устроена независимая проверка другими моделями

После исправления масштабирования одни и те же сохранённые результаты оценивают:

1. DeepSeek;
2. выбранная доступная GPT-модель;
3. Claude Opus;
4. два человека по той же рубрике.

Названия методов скрываются и перемешиваются. Итог сравнивается по formal E2E,
LLM-score, согласию судей, устойчивости повторов, токенам, времени и стоимости.
Это уменьшает риск того, что DeepSeek предпочитает результаты, созданные
DeepSeek.
