# Агенты, оркестратор, валидатор и критик

Эта заметка отвечает на вопросы для защиты: сколько в системе агентов, как они
связаны, что делает корневой оркестратор, зачем нужна детерминированная
проверка, чем validator (валидатор) отличается от critic (критика) и что уже
действительно реализовано.

Разбор повторяемости одного входа, точной роли критика и semantic composite
вынесен в [[21_КАК_ЧИТАТЬ_SEMANTIC_И_ЗАЧЕМ_НУЖЕН_КРИТИК]].

![[assets/06_agents_orchestrator_validation.png]]

> [!important] Короткий правильный ответ
> В системе **два агента**: `Use Case Agent` (агент вариантов использования) и
> `Activity Diagram Agent` (агент диаграмм активности). Их связывает `Root
> Graph` (корневой граф-оркестратор). `Generator`, `Critic` и `Repair` — это
> внутренние роли и вершины агентов, а не шесть самостоятельных агентов.

## Точная короткая схема выполнения

Предложенная пользователем линия верна как сокращение, но в полном виде есть
два отдельных цикла проверки:

```text
SpecificationReq
→ normalize FR/NFR (нормализация требований и стабильные ID)
→ Use Case Agent
   → generator → schema → deterministic validator
   → [формальная ошибка: сразу decide] / [формально корректно: critic → decide]
   → accept / bounded repair → повторная schema-проверка / controlled failure
→ Activity Diagram Agent × каждый принятый UC
   → generator → schema → deterministic validator
   → [формальная ошибка: сразу decide] / [формально корректно: critic → decide]
   → accept / bounded repair → повторная schema-проверка / controlled failure
   → Mermaid renderer
→ объединение TraceManifest
→ E2E trace validation
→ evaluator
→ GeneratedSpecification
```

Critic (критик) намеренно пропускается, если обычный Python-валидатор уже нашёл
блокирующую формальную ошибку. Это уменьшает расход токенов: сначала исправляется
проверяемая структура, затем LLM оценивает смысл.

## 1. Что такое вершина и ребро графа

`Node` (вершина графа) — отдельная операция над общим состоянием. Вершина
получает типизированный state (состояние), выполняет одну ответственность и
возвращает только изменившиеся поля.

Примеры вершин:

- нормализация требований;
- генерация набора Use Cases;
- проверка схемы;
- детерминированная проверка;
- семантическая критика;
- выбор следующего перехода;
- исправление;
- финализация.

`Edge` (ребро графа) — разрешённый переход между вершинами. Ребро само по себе
не «думает». Оно задаёт порядок выполнения или выбирается router (маршрутизатором)
по состоянию.

В условном ребре решение зависит от поля `decision`:

- `finalize` — результат можно принять;
- `repair` — ошибки можно попробовать исправить;
- `fail` — лимит исчерпан или результат нельзя принять.

## 2. Корневой граф-оркестратор

`Root Graph` (корневой граф) не является третьим агентом. Это управляющий
workflow (рабочий процесс), который передаёт данные между двумя специализированными
агентами и собирает итоговый результат.

В коде корневой граф содержит шесть рабочих вершин:

1. `normalize_requirements` — превращает строковые ФТ/НФТ во внутренние модели,
   присваивает стабильные `FR-001`, `NFR-001` и создаёт начальный trace manifest
   (реестр связей).
2. `run_use_cases` — запускает первый подграф и получает `UseCaseSet`.
3. `run_activities` — последовательно запускает второй подграф для каждого Use
   Case. Параллельный fan-out (разветвлённый запуск) пока запланирован, но не
   реализован.
4. `validate_e2e_trace` — проверяет сквозные связи между требованиями, Use Case
   и activity-диаграммами.
5. `run_evaluator` — рассчитывает формализованные метрики.
6. `finalize_pipeline` — собирает `GeneratedSpecification` (итоговую
   спецификацию).

На уровне исходного кода у root graph шесть рабочих вершин и семь линейных
рёбер, если считать служебные переходы `START` и `END`.

### Зачем нужен оркестратор

- гарантирует единый порядок этапов;
- не позволяет Activity Agent работать без принятого Use Case;
- передаёт стабильные идентификаторы и trace-связи;
- собирает отчёты всех проверок;
- формирует единый статус `success`, `partial` или `failed`;
- даёт место для будущего checkpoint/resume (сохранения и продолжения).

> [!presentation] Что оставить на слайде
> Одна линия: `SpecificationReq → normalize → Use Case Agent → Activity Agent ×
> UC → trace validation → evaluator → result`. Подпись: «Оркестратор управляет
> этапами, но сам не является агентом».

## 3. Агент 1: Use Case Agent

### Вход

- нормализованный `SpecificationRequest`;
- функциональные и нефункциональные требования со стабильными ID;
- лимит исправлений.

### Выход

- `UseCaseSet` (набор вариантов использования);
- акторы;
- основной, альтернативные и ошибочные сценарии;
- user stories и system stories;
- `TraceManifest` со связями `FR → UC`;
- отчёты проверки и итоговый статус.

### Внутренние вершины

1. `prepare_requirements` — подготавливает состояние.
2. `generate_use_case_set` — generator (генератор) предлагает структурированный
   набор UC и связи.
3. `validate_uc_schema` — Pydantic проверяет форму и типы.
4. `validate_uc_deterministic` — обычный Python-код проверяет инварианты.
5. `criticize_use_case_set` — critic (критик) оценивает смысл.
6. `decide_uc_result` — router выбирает принять, исправить или завершить с
   ошибкой.
7. `repair_use_case_set` — repair (исправление) получает конкретный список
   ошибок и формирует исправленный артефакт.
8. `finalize_use_case_set` — принимает результат.
9. `fail_use_case_generation` — возвращает контролируемую ошибку.

У подграфа девять рабочих вершин и тринадцать логических рёбер, если считать
три исхода router и служебные `START`/`END`.

### Текущий статус реализации

Для generator, critic и repair реализованы функции, работающие через общий
`LLMClient` (клиент языковой модели). `compile_pipeline` специально создаёт
безопасный offline-граф со stub (заглушками), а `compile_live_pipeline` явно
подключает реального провайдера к обоим агентам. Живой UC-контур уже проверен в
повторном пилоте; он не включается неявно, чтобы тест или импорт модуля не начал
расходовать API-токены.

## 4. Агент 2: Activity Diagram Agent

### Вход

- один принятый Use Case;
- общий список акторов;
- уже существующий `TraceManifest`;
- лимит исправлений.

### Выход

- типизированная `ActivityDiagram`;
- partitions (дорожки участников), nodes (узлы) и edges (переходы);
- связи узлов диаграммы с шагами Use Case;
- Mermaid-код как производное представление;
- отчёты и статус.

### Внутренние вершины

1. `prepare_use_case`;
2. `generate_activity_model`;
3. `validate_activity_schema`;
4. `validate_activity_deterministic`;
5. `criticize_activity_model`;
6. `decide_activity_result`;
7. `repair_activity_model`;
8. `render_mermaid`;
9. `finalize_activity`;
10. `fail_activity_generation`.

У подграфа десять рабочих вершин и четырнадцать логических рёбер с учётом трёх
исходов router и `START`/`END`.

### Текущий статус реализации

Pydantic-модель, детерминированные проверки, router, Mermaid-renderer и live
generator/critic/repair реализованы. FULL DEV-001 дважды завершился успешно и
исправил формальные edge defects. Это подтверждает механизм, но не результат на
всех 20 DEV.

## 5. Что означает детерминированная проверка

Детерминированная проверка — это проверка обычным кодом без вызова LLM. Для
одинакового входа и одной версии кода она возвращает одинаковый результат.

Пример: если в исходе есть `FR-001`, `FR-002`, `FR-003`, валидатор собирает все
`source_fr_ids` у Use Cases и вычисляет разность множеств. Если `FR-003` нигде
не встречается и не имеет явного допустимого статуса, результат всегда будет
`fr_uncovered`. Здесь не требуется субъективная оценка модели.

### Зачем она нужна

- формальные ошибки находятся точно и повторяемо;
- один и тот же результат можно перепроверить без LLM;
- ошибки получают стабильный `code` и список `element_ids`;
- repair получает конкретную задачу вместо просьбы «сделай лучше»;
- снижается риск, что вероятностный critic пропустит битую ссылку;
- такие проверки дешевле и быстрее LLM-вызова.

В текущем графе deterministic validator выполняется **до** critic. Если найдена
формальная blocking error, conditional short-circuit пропускает платный critic
и направляет объект в decide/repair. После успешного формального исправления
critic проверяет смысл.

## 6. Что проверяют валидаторы

### Schema validator (валидатор схемы)

Pydantic проверяет:

- наличие обязательных полей;
- тип каждого поля;
- допустимые значения enum (перечислений);
- формат вложенных объектов;
- запрет неизвестных полей в строгих моделях.

Schema validator отвечает на вопрос: «Можно ли вообще безопасно обработать этот
JSON как ожидаемую модель?»

### Use Case deterministic validator

Он проверяет:

- уникальность ID;
- наличие хотя бы одного Use Case и акторов;
- цель, основного актора и основной сценарий;
- наличие и порядок шагов;
- наличие `source_fr_ids`;
- отсутствие ссылок на несуществующие FR;
- покрытие каждого функционального требования или явный статус непокрытия;
- наличие каждой обязательной связи `FR_TO_UC`;
- отсутствие dangling links (ссылок на несуществующий объект);
- отсутствие необоснованных предположений.

### Activity deterministic validator

Он проверяет:

- ровно один initial node (начальный узел);
- хотя бы один final node (конечный узел);
- существование source и target для каждого ребра;
- минимум две исходящие ветки у decision node;
- guard condition (условие) на каждой ветке решения;
- трассировку action/decision до шага Use Case либо явную отметку `unsupported`;
- достижимость значимых узлов от начала;
- достижимость завершения;
- отсутствие ссылок на неизвестные шаги Use Case.

### End-to-end trace validator

После обоих агентов он повторно проверяет глобальную уникальность ID, покрытие
ФТ и целостность всех сквозных trace-ссылок.

### Почему выбран именно такой набор

Правила соответствуют четырём главным рискам проекта:

1. **Потеря требований** → проверка покрытия ФТ.
2. **Галлюцинация элементов** → проверка источников, ссылок и предположений.
3. **Неработающая диаграмма** → проверка узлов, рёбер, ветвлений и достижимости.
4. **Невозможность обратного редактирования** → стабильные ID и двусторонний
   trace.

Это не полная формальная проверка всего стандарта UML. Реализуется выбранный
профиль activity semantics (семантики диаграммы активности), достаточный для
сценариев Use Case и исследуемой трассировки.

## 7. Как происходит критика

Critic (критик) — отдельный LLM-вызов после структурных проверок. Он получает:

- исходную спецификацию;
- текущий структурированный артефакт;
- отчёты schema и deterministic validation;
- критерий вернуть `accept` или `repair`;
- список семантических `ValidationIssue`.

Критик нужен для вопросов, которые трудно свести к простому сравнению ID:

- правильно ли определена цель Use Case;
- соответствует ли сценарий смыслу требования;
- разумно ли выделены границы разных Use Cases;
- не являются ли два UC смысловыми дублями;
- не потеряно ли важное альтернативное или ошибочное поведение;
- не выдумана ли бизнес-логика, отсутствующая во входе.

Если есть блокирующие ошибки, router направляет состояние в repair. Repair
получает текущий артефакт, список ошибок и номер попытки. После исправления
результат снова проходит schema и deterministic validation, затем critic.
Количество повторов ограничивает `max_repair_attempts`; бесконечного цикла нет.

### Честное ограничение текущей версии

UC и Activity critic имеют live-реализацию и явно подключаются через
`compile_live_pipeline`. Рубрика машинной критики не заменяет gold и двух
экспертов; candidate semantic threshold калибруется только на DEV.

> [!presentation] Что оставить на слайде
> `LLM generator → Pydantic schema → deterministic validator → LLM critic →
> router → accept / bounded repair / controlled failure`. Под схемой: «Код
> проверяет факты и ссылки; LLM проверяет смысл; каждый найденный дефект имеет
> код и привязку к элементам».

## 8. Как два агента связаны

Первый агент формирует единое смысловое основание — Use Cases. Только после его
успешного завершения root передаёт каждый Use Case второму агенту. Второй агент
не перечитывает исходные требования и не придумывает новый сценарий с нуля: он
должен отобразить уже согласованный сценарий в типизированный граф.

Связь обеспечивают стабильные идентификаторы:

```text
FR-001
  → UC-001
    → SC-001
      → STEP-001
        → NODE-001
          → EDGE-001
```

За счёт этого можно пройти от требования к картинке и обратно от выбранного
элемента диаграммы к исходному требованию.

## 9. Отличие от статического анализа кода

В созвоне 2026-08-05 обсуждалась другая схема: после появления кода готовые
инструменты могут извлечь классы, пакеты и зависимости и построить UML. Это
`code-to-UML` (код в UML), тогда как наша задача — `requirements-to-Use
Case/activity` (требования в сценарии и диаграммы активности) **до кода**.

Точная библиотека в созвоне не была названа. На вопрос «на каких технологиях?»
руководитель в 00:13:11–00:13:16 ответила, что не помнит, потому что этим
занимается другая команда. Поэтому нельзя приписывать разговору конкретный
инструмент.

Для воспроизводимой локальной проверки выбран Pyreverse:

- версия первого запуска: Pylint/Pyreverse 4.0.8;
- проанализировано 22 Python-модуля и 34 импорта;
- получено 439 строк Mermaid class diagram;
- получено 79 строк Mermaid package diagram;
- вызов LLM и API-ключ не требуются.

Артефакты лежат в `artifacts/baselines/static_analysis_pyreverse/`, повторный
запуск выполняется командой:

```bash
./scripts/run_static_analysis_baseline.sh
```

Этот baseline полезен для ответа комиссии и демонстрации различия входов, но не
является прямым конкурентом по нашим метрикам activity-сценариев: он начинает с
готового Python-кода и строит структурную, а не поведенческую диаграмму.
