# Release candidate (кандидат на выпуск) и полный B0 DEV20

## Что закончено технически

Добавлена одна команда `traceable-spec` (запуск спецификации), которая принимает
JSON `SpecificationReq` и создаёт в одном каталоге полный комплект результатов:
Use Cases (варианты использования), User/System Stories (пользовательские и
системные истории), Activity Mermaid (исходники диаграмм активности),
TraceManifest (манифест трассировки), validation reports (отчёты проверок) и
quality report (отчёт качества).

Команда не перезаписывает непустой каталог. Для сетевого `FULL` (полного графа)
нужно явно указать `--allow-live`; ключ в результаты не записывается. Ошибка не
маскируется: артефакты сохраняются, а процесс завершается ненулевым кодом.

Подробная инструкция: `../release/REPRODUCIBILITY_AND_DEMO.md`.

## Полный бесплатный эксперимент B0

`B0_RULE` (детерминированный baseline, базовый ориентир на правилах) запущен на
всех 20 DEV-кейсах по три раза: 60 из 60 запусков завершились, стабильность
между повторами равна 1,0, расход LLM-токенов — ноль.

![[assets/13_b0_dev20_quality.png]]

При этом semantic composite (сводная смысловая метрика) равна 0,408, 95%
bootstrap interval (бутстрэп-интервал) — `[0,356; 0,463]`, а hallucination proxy
(индикатор неподтверждённых элементов) — 0,493. Это показывает различие между
формальной корректностью и смысловой точностью: правила стабильно создают
валидный граф, но плохо распознают акторов, ветвления и предметные сценарии.

Первичные данные и расчёт:

- `artifacts/benchmark_runs/b0-dev20-r3-2026-09-09/`;
- `artifacts/research_summary_2026-09-09/b0_dev20_summary.json`;
- `docs/research/B0_DEV20_RESULTS_2026_09_09.md`.

## Что теперь проверяет CI

`CI` (автоматическая проверка в GitHub) работает только offline (без сети и
платных токенов): проверяет lock-файл, стиль, типы, 56 тестов, 30 benchmark-
кейсов, freeze hashes (контрольные хэши), mutation suite 15/15 и сборку пакета.

## Какие три конфигурации собственной системы сравнивать

- `FULL` (полный граф) — critic (критик) и repair (исправление) включены;
- `FULL_NO_CRITIC` — детерминированные проверки и repair остаются, но обе
  семантические роли критика отключены;
- `FULL_NO_REPAIR` — критики и проверки остаются, но лимит исправлений равен
  нулю, поэтому отказ становится контролируемым сразу.

Это именно component variant (варианты без отдельных компонентов) собственной архитектуры. `B0_RULE` и
`B1_ONESHOT` остаются baseline (базовыми ориентирами). Отключать
детерминированный validator в production path не следует: тогда структурно
ошибочный результат может быть объявлен успешным. Его вклад отдельно доказан
mutation suite 15/15.

## Сколько будет стоить следующий шаг

Расчёт по сохранённому DEV-001 показывает для трёх репрезентативных кейсов один
раз около 212 070 токенов и $0,15 по пиковому тарифу. Предложенный защитный
предел: 60 calls, 450 000 tokens и $0,40. Полный B1/FULL DEV20 × 3 оценивается
примерно в 4,41 млн токенов и $3,20, консервативный предел — $7. Эти числа нужно
пересчитать после малого пилота; без явного разрешения платный вызов не делается.

Если сразу включить на этих трёх кейсах все четыре live-условия — B1, FULL и
два варианта без отдельных компонентов — консервативный прогноз равен 546 520 токенов, 125 calls и $0,38;
защитные пределы: 160 calls, 1,2 млн токенов и $0,90. Пока варианты без отдельных компонентов не измерены,
для каждой из них в расчёте используется расход FULL, поэтому оценка намеренно
завышена.

## Что ещё нельзя отметить выполненным

- B1/FULL ещё не прогнаны на всех 20 DEV-кейсах;
- нет двух независимых экспертных оценок;
- нет письменного согласования руководителя;
- scientific freeze (научная фиксация) и hidden run не выполнялись;
- публикация benchmark должна быть отдельно разрешена.
