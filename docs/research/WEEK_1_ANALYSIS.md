# Неделя 1 — анализ постановки

Дата: **2026-08-21**  
Автор каркаса: Артём Боцман  
Тема НИР: *Разработка и исследование трассируемого пайплайна генерации структурированных Use Cases и activity-диаграмм по функциональным требованиям*.

## 1. Уточнённая постановка

Система принимает внешний `SpecificationReq` (`project_task`, название, цель,
описание проекта, списки строк ФТ и НФТ), детерминированно нормализует его во
внутренний `SpecificationRequest` со стабильными ID и формирует:

- набор Use Cases со сценариями, user/system stories и человекочитаемым текстом;
- структурированную activity-модель на каждый UC;
- детерминированный Mermaid-код как *производное* представление;
- единый `TraceManifest` (ФТ → UC → шаги → узлы/рёбра activity);
- отчёты schema / structural / trace / (позже) semantic LLM-критики;
- итоговый отчёт автоматических метрик качества.

Ключевая особенность — **не** one-shot «текст → Mermaid», а управляемый agentic workflow на LangGraph: LLM-узлы + детерминированные валидаторы + ограниченный repair-loop.

## 2. Потребители диаграмм

| Потребитель | Зачем activity / UC |
|-------------|---------------------|
| Аналитик / автор требований | Проверка полноты и согласованности ФТ до реализации |
| Архитектор / тимлид | Согласование поведения и границ системы |
| Разработчик | Спецификация сценариев до кода |
| Тестировщик | Основа для сценариев приёмки |
| Комиссия / научный руководитель | Воспроизводимые артефакты и трассировка для оценки метода |

Диаграммы нужны **до** генерации кода: они фиксируют намерение поведения и обеспечивают проверяемую связность с требованиями.

## 3. Почему диаграмма строится до кода

1. Требования часто неоднозначны; ранняя визуализация поведения выявляет пробелы.
2. Трассировка ФТ → UC → activity даёт auditable цепочку до реализации.
3. Исправление модели дешевле исправления кода.
4. Последующая генерация кода/тестов может опираться на уже провалидированную модель (вне текущего этапа).

## 4. Почему статический анализ кода не решает задачу

Статический анализ работает по **уже существующему** коду и не:

- не восстанавливает намерение стейкхолдера из ФТ;
- не строит согласованные Use Cases и user/system stories;
- не обеспечивает покрытие требований «сверху вниз»;
- не заменяет спецификацию для систем, которых ещё нет.

Задача НИР — **синтез спецификации из требований**, а не reverse engineering.

## 5. Почему прямой LLM-to-Mermaid недостаточен

По систематическому обзору Rahmanian et al. (arXiv:2607.26100) для LLM-генерации UML/ER типичны:

- семантические неточности и галлюцинированные элементы;
- слабая согласованность между представлениями;
- неоднородные метрики и редкий reuse бенчмарков;
- зависимость от формулировки промпта и вендора модели.

Прямой вывод Mermaid:

- смешивает синтаксис диаграммы с семантикой сценария;
- затрудняет детерминированную валидацию и трассировку;
- делает repair непрозрачным (править строку vs модель).

Поэтому **источник истины** — `ActivityDiagram`; Mermaid — чистая функция `ActivityDiagram → str`.

## 6. Исследовательские вопросы

- **RQ1.** Улучшает ли структурированное промежуточное представление полноту и корректность по сравнению с прямой one-shot генерацией UC и Mermaid?
- **RQ2.** Как детерминированные валидаторы и LLM-критик влияют на покрытие ФТ, число структурных ошибок и успешность end-to-end запуска?
- **RQ3.** Повышает ли детерминированный рендер Mermaid из общей смысловой модели согласованность UC и activity diagram?
- **RQ4.** Как меняются полнота, трассируемость и устойчивость генерации при увеличении количества и сложности ФТ?
- **RQ5.** Как ограничение количества repair-итераций влияет на качество, стоимость и гарантированное завершение pipeline?

Утверждение «наш метод лучше baseline» **не делается заранее** — только экспериментально.

## 7. Обзор аналогов (кратко)

| Направление | Наблюдение | Отношение к НИР |
|-------------|------------|-----------------|
| LLM → UML class/sequence (обзор 2023–2025) | Доминируют class diagrams; behavioural diagrams underrepresented | Activity/UC — осознанный пробел |
| One-shot Mermaid-чатботы | Быстро, но без контрактов и трассировки | Baseline для RQ1/RQ3 |
| Классический RE / трассируемость | Зрелые модели связей, мало LLM | Берём идею единого манифеста связей |
| Соседний `AppFactory-agents` | Существует как предшествующий внутренний опыт | **Не переиспользуется**: иная постановка, риск ограничений на публикацию; новое open-source решение со своей моделью |

Источники проектирования: LangGraph Graph API / subgraphs / workflows; Pydantic v2; UML 2.5.1; Mermaid flowchart/stateDiagram; arXiv:2607.26100.

## 9. Ожидаемая новизна

**Научная:** эмпирическое сравнение structured intermediate representation + deterministic validators + bounded repair против one-shot LLM-to-Mermaid на воспроизводимом benchmark с раздельными метриками.

**Практическая:** open-source каркас трассируемого pipeline с явными контрактами, пригодный для расширения на реальные LLM через LiteLLM/OpenAI-compatible API.
