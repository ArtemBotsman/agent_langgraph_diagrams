# Агентная генерация Use Case и activity-диаграмм по требованиям

## Аннотация

Разработан воспроизводимый LangGraph pipeline (конвейер), который принимает
структурированный `SpecificationReq`, формирует Use Cases, user stories, system
stories и activity-диаграммы, а затем проверяет структуру и двустороннюю
трассировку. В системе работают два агента: Use Case Agent и Activity Diagram
Agent. Корневой граф оркестрирует их, материализует TraceManifest и запускает
evaluator. LLM-критика и ограниченное исправление дополняют детерминированные
валидаторы, но не заменяют их.

Технический benchmark candidate содержит 30 авторских синтетических кейсов:
20 development и 10 hidden. Валидация benchmark проходит для 30/30 кейсов,
mutation-suite обнаруживает 15/15 заявленных классов структурных и
трассировочных дефектов. Rule-based baseline B0 прогнан на всех 20 DEV-кейсах
по три раза. Получено 60/60 технических завершений, stability 1.0 и semantic
composite 0.408 с case-level bootstrap 95% CI [0.356; 0.463]. Этот результат
показывает воспроизводимость B0 и одновременно его недостаточное смысловое
качество.

Первый повторный live pilot на DEV-001 сравнил B0, B1 one-shot и FULL. Затем на
трёх одинаковых DEV-кейсах разной сложности сравнили пять конфигураций. После
уточнения контракта критика FULL завершил 3/3 запуска, получил semantic
composite 0.714 и trace F1 0.933. B1 one-shot и вариант без повторного
исправления получили 0/3 сквозных завершений. Пилот показывает необходимость
контролируемого исправления, но не доказывает преимущество критика: вариант без
него также завершил 3/3 запуска. Для итогового вывода нужны повторы на DEV20 и
две независимые экспертные оценки.

## 1. Постановка задачи

### 1.1. Контекст

Текущая НИР ограничена генерацией аналитико-архитектурных артефактов до
написания кода. Исторический проект полного жизненного цикла разработки ПО
служит контекстом, но не входит в текущий scope (границы работы).

### 1.2. Цель

Цель работы состоит в разработке и исследовании агентного конвейера, который
преобразует подготовленные функциональные и нефункциональные требования в
структурированные Use Cases, stories и activity-диаграммы с машинно
проверяемой трассировкой.

### 1.3. Исследовательские вопросы

1. RQ1. Улучшает ли многостадийный pipeline качество по сравнению с one-shot
   генерацией при одинаковом входе, модели и выходном контракте?
2. RQ2. Какой вклад дают critic и bounded repair?
3. RQ3. Обеспечивает ли typed trace model полноту и ссылочную целостность?
4. RQ4. Как меняются качество, стабильность, задержка и расход токенов с ростом
   сложности требований?

## 2. Вход и выход системы

`SpecificationReq` содержит шесть полей: `project_task`, `project_name`,
`project_goal`, `project_description`, `functional_requirements` и
`non_functional_requirements`.

Один запуск формирует:

- типизированный набор Use Cases и акторов;
- текстовые UC, user stories и system stories;
- типизированные activity-модели и Mermaid source;
- TraceManifest с прямыми и обратными ссылками;
- validation reports и evaluation report;
- run manifest, token/cost telemetry и SQLite checkpoints для FULL.

## 3. Архитектура

В системе два исполняемых агента. Use Case Agent преобразует требования в UC и
stories. Activity Diagram Agent строит поведенческий граф для каждого UC.
Корневой orchestrator (оркестратор) вызывает подграфы, объединяет результаты,
строит трассировку и вычисляет итоговые метрики.

Статическая структура включает 25 рабочих вершин. При едином способе подсчёта
LangGraph показывает 36 возможных переходов с учётом технических START/END и
всех исходов условных маршрутизаторов: root graph содержит 6 рабочих вершин и
9 переходов, UC subgraph — 9 вершин и 13 переходов, Activity subgraph — 10
вершин и 14 переходов. Если технические START/END исключить во всех трёх
графах, остаётся 28 внутренних переходов. Ранее использовавшееся число 32
относилось к версии до добавления двух ветвей раннего пропуска critic при
формальной ошибке.

Каждый агент использует последовательность generate, schema validation,
deterministic validation, critic, decision и bounded repair. Формальная ошибка
направляет результат в исправление до платного critic-вызова. Число повторов
ограничено `max_repair_attempts`, поэтому цикл гарантированно завершается.

## 4. Трассировка и валидация

Основная цепочка происхождения:

`FR -> requirement atom -> UC -> scenario step -> activity node/edge`.

LLM выбирает типизированные source IDs, а Python детерминированно создаёт
единый TraceManifest. Валидаторы проверяют уникальность ID, типы концов связи,
висячие ссылки, прямую и обратную полноту, достижимость activity graph,
guard-условия и provenance (происхождение) неподдержанных элементов.

Порог UC trace coverage установлен не ниже 95%. Для activity elements требуется
100%: каждый узел и каждое ребро имеют источник в UC либо явную маркировку
unsupported с объяснением.

Mutation-suite содержит 15 заранее определённых классов ошибок. Валидаторы
обнаруживают 15/15. Это утверждение относится только к заявленным классам и не
означает обнаружение любой возможной семантической ошибки.

## 5. Benchmark и методика

Benchmark candidate содержит 30 кейсов: 20 DEV и 10 hidden, 8 простых, 13
средних и 9 сложных, 13 русскоязычных и 17 англоязычных. Gold-разметка включает
акторов, UC, milestones, ветвления и FR-to-UC связи. Эквивалентные формулировки
задаются через canonical slots и допустимые aliases.

Автоматическая оценка разделяет:

- schema/structural validity;
- trace integrity и coverage;
- semantic slot matching для акторов, UC, milestones и branches;
- hallucination proxy;
- latency, tokens, cost, repairs и stability;
- итоговый E2E gate.

Semantic composite является dashboard metric. Он не заменяет отдельные
измерения и экспертную оценку. Hidden inputs отделены от sealed hidden gold и
не используются для настройки.

## 6. Сравниваемые конфигурации

- B0_RULE: детерминированный нижний ориентир без LLM.
- B1_ONESHOT: один вызов той же LLM без критики и исправления.
- FULL: два агента, валидаторы, critic и bounded repair.
- FULL_NO_CRITIC: вариант без отдельного компонента семантической критики.
- FULL_NO_REPAIR: вариант без отдельного компонента цикла исправления.

Pyreverse используется как adjacent baseline (смежный ориентир) для
code-to-UML. Он получает существующий Python-код и поэтому не является прямым
соперником requirements-to-diagram pipeline. GitDiagram и DeepWiki также
ориентированы на репозиторий, а не на входные бизнес-требования до кода.

## 7. Результаты

### 7.1. Live pilot DEV-001

B0 получил E2E 1.0 и semantic 0.633 при нулевом расходе токенов. B1 получил
semantic 0.724, но E2E 0.0 из-за activity edge trace coverage. FULL получил E2E
1.0 и semantic 0.670, использовал в среднем 33 445 токенов и два repair. Более
высокий semantic composite B1 не компенсировал формальный дефект.

Error analysis подтвердил: два запуска B1 содержали 8 случаев
`activity_edge_untraced` и 2 случая
`activity_trace_coverage_below_threshold`. FULL обнаружил четыре промежуточных
`activity_edge_untraced`, затем исправил их; в финальном результате
неразрешённых blocking issues нет.

### 7.2. Полный B0 DEV20

Три повтора каждого DEV-кейса дали 60/60 технических завершений и stability
1.0. Средний semantic composite равен 0.408. По сложности: simple 0.543,
medium 0.359, hard 0.335. Hallucination proxy в среднем равен 0.493. Semantic
composite ниже 0.5 получен у 15 из 20 уникальных кейсов; поскольку каждый кейс
повторялся три раза без изменений, это соответствует 45 из 60 запусков. В 48
из 60 запусков hallucination proxy выше 0.4.

Повторная агрегация из сохранённых `results.json`, `results.csv` и run bundles
совпадает с исходными метриками для обоих проведённых экспериментов. Проверка
не вызывает LLM и фиксирует SHA-256 исходных результатов.

### 7.3. Сравнение пяти конфигураций на трёх DEV-кейсах

В пилот вошли B1-DEV-002, B1-DEV-010 и B1-DEV-020: простой русский, средний
русский и сложный английский кейсы. Для каждой конфигурации выполнено по одному
запуску на кейс. Все LLM-конфигурации использовали `deepseek-flash`,
`temperature=0`, один endpoint и одинаковые входы; hidden не открывался.

- B0: 3/3 E2E, semantic 0.524, branch F1 0.000, trace F1 0.857, 0 токенов.
- B1 one-shot: 0/3 E2E, semantic 0.487, в среднем 10 358 токенов и 0.0046 USD
  на запуск.
- FULL после уточнения контракта критика: 3/3 E2E, semantic 0.714, branch F1
  0.690, trace F1 0.933, в среднем 52 947 токенов и 0.0294 USD на запуск.
- Вариант без критика: 3/3 E2E, semantic 0.699, trace F1 0.952, в среднем
  37 011 токенов и 0.0238 USD на запуск.
- Вариант без исправления: 0/3 E2E при semantic 0.730 и trace F1 0.952; в
  среднем 9 380 токенов и 0.0065 USD на запуск.

B0 подтверждает, что прохождение структурного барьера не равно высокому
смысловому качеству: он не восстановил ветвления. Вариант без исправления,
наоборот, получил высокий автоматический содержательный балл, но не сформировал
принимаемый полный пакет. Поэтому semantic composite нельзя использовать без
E2E gate. Прямой one-shot оказался примерно в 6.4 раза дешевле FULL, но не дал
ни одного принимаемого результата на выбранных кейсах.

Первоначальный FULL завершил только 1/3 запусков: критик мог вводить новый
критерий после каждого исправления. После изменения контракта блокирующее
замечание обязано ссылаться на конкретное требование и элемент модели, а стиль
не блокирует результат. Завершение выросло до 3/3, но средняя стоимость - с
0.0239 до 0.0294 USD. Это подтверждает устранение инженерной ошибки, но не
является статистическим доказательством полезности критика.

### 7.4. Финальное development-сравнение B0/B1/FULL

На одинаковом frozen DEV20 выполнены три повтора каждого метода: 20 проектов ×
3 повтора × 3 метода = 180 сохранённых результатов. Независимой единицей
статистического анализа считается проект; повторы сначала усредняются внутри
проекта. Использованы 50 000 кластерных bootstrap-выборок, точный парный
двусторонний sign-flip test и поправка Holm для трёх заранее выбранных
сравнений.

- `B0_RULE`: E2E 60/60, semantic 0,408, 0 LLM-токенов;
- `B1_ONESHOT`: E2E 2/60, semantic 0,595, в среднем 10 565 токенов и 15,5 с;
- `FULL`: E2E 60/60, semantic 0,693, в среднем 62 046 токенов и 57,1 с.

FULL повысил E2E относительно B1 на 96,7 процентного пункта; 95% CI
`[+91,7; +100,0]`, Holm-adjusted `p=5,72×10⁻⁶`, положительная разница на 20
из 20 проектов. Относительно B0 semantic composite вырос на 0,285; 95% CI
`[+0,224; +0,342]`, Holm-adjusted `p=7,63×10⁻⁶`, FULL лучше на 19 из 20
проектов. При учёте незавершённых B1-ответов как нулевого результата разница
FULL−B1 по semantic равна +0,098; 95% CI `[+0,029; +0,174]`, Holm-adjusted
`p=0,0157`.

Среди только разобранных B1-ответов semantic равен 0,700 против 0,693 у FULL.
Поэтому основной подтверждённый вклад полного графа — надёжное доведение
результата до схемы и трассировочного контракта. Нельзя утверждать, что FULL
улучшает содержание каждого уже завершённого one-shot-ответа. Цена надёжности:
примерно в 5,9 раза больше токенов и в 3,7 раза больше времени.

Полная методика, график и машинные результаты находятся в
`docs/research/DEV20_FINAL_STATISTICAL_EVIDENCE_2026_09_13.md` и
`artifacts/final_dev20_statistical_evidence_2026-09-13/`.

## 8. Надёжность и воспроизводимость

OpenAI-compatible adapter повторяет только временные ошибки 408, 409, 425,
429 и 5xx, учитывает `Retry-After` и ограничивает задержку. Ошибки 400, 401 и
403 не повторяются. Действуют лимиты числа вызовов, токенов и оценочной
стоимости.

Public run bundle хранит хэши prompt/response и sanitized telemetry. Точное raw
evidence можно включить только явно через `--capture-raw-private-dir`.
Приватный каталог получает права 700, файлы - 600, API key туда не записывается,
путь не попадает в публичный run config. `.private_experiment_evidence/`
исключён из Git.

CI выполняет Poetry lock check, Ruff, mypy, тесты, benchmark/freeze/mutation
checks, offline verification сохранённых экспериментов и package build. Live и
hidden вызовы в CI отсутствуют.

## 9. Ограничения валидности

Benchmark создан автором и имеет technical author freeze, но не прошёл две
независимые экспертные проверки. Сравнение B0/B1/FULL охватывает все 20
development-проектов и три повтора, поэтому порог E2E ≥90% для FULL на DEV
подтверждён. Semantic matcher и его порог не откалиброваны по экспертам. Alias
`deepseek-flash` может менять внутреннюю ревизию модели. Обобщаемость за
пределы DEV20 требует однократного sealed hidden-run после научной фиксации и
внешнего сравнения на точных версиях GPT/Claude.

## 10. Вывод

Разработан полный исполняемый контур от `SpecificationReq` до трассируемых
activity-диаграмм и отчёта качества. Детерминированные проверки обнаруживают
структурные дефекты, а ограниченный agentic repair способен исправить
непротрассированные элементы в live pilot. B0 доказывает воспроизводимость
методики, но показывает недостаточность простых правил для смысловой задачи.

Инженерный release candidate готов. На frozen DEV20 статистически подтверждено,
что FULL значительно надёжнее прямого one-shot по полному E2E-критерию и
семантически сильнее детерминированного B0. Отдельная полезность именно критика
этим сравнением не доказана: для неё нужен повторный запуск вариантов
`FULL_NO_CRITIC` и `FULL_NO_REPAIR`. Научное завершение требует согласования
правил, двух независимых экспертов, внешнего сравнения и единственного
sealed hidden-run после scientific freeze.
