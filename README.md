# Проверяемые Use Cases и Activity Diagrams из требований

AgentLangGraph преобразует функциональные и нефункциональные требования в
типизированный пакет: Use Cases, сценарные шаги, Activity Diagrams, Mermaid и
TraceManifest. Пакет предназначен для разработчика или агента-кодера;
система не генерирует полную архитектуру программного кода.

**Цель** — повысить качество и надёжность подготовки аналитических артефактов
перед кодогенерацией. Реализованы явные ссылки от требований к сценариям и
диаграммам, проверка согласованности и ограниченное исправление.
Формальная корректность и смысловая полнота оцениваются раздельно.

## Архитектура и исправления

Оркестратор LangGraph запускает два специализированных графа: Use Cases,
затем Activity для каждого сценария. В каждом есть генератор, критик и редактор
— всего шесть ролей LLM. Формальные валидаторы работают программно, без модели.
При формальных ошибках критик может быть пропущен. Допускается до двух
исправлений на соответствующий цикл; граф может завершиться отказом.

Исправлено:

- полный исходный контекст передаётся всем шести ролям;
- редактор получает замечания к текущей версии, отдельно от истории;
- критик и редактор Activity получают словарь акторов;
- проверяются начало, конец и достижимость действий; обход не продолжается после конца;
- добавлены общий оценщик, потоковая сборка ответов и учёт обрезаний;
- добавлены baseline с одной правкой, разбиение по UC и внешний OpenCode.

Критик и раньше получал актуальный сгенерированный результат. Исправление
касается полноты исходного контекста и передачи замечаний.

V1/V2 — версии правил проверки. В V2 служебный переход к началу/концу может
не иметь ссылки на шаг при строгих структурных условиях. Ссылки для
бизнес-действий и ветвлений по-прежнему проверяются.

## Как сравнивались FULL и OpenCode

OpenCode **не входит в FULL**. Стенд отдельно запускал наш граф и настоящий
OpenCode **Build 1.18.33**, не Plan и не NOMAD. OpenCode разрешались чтение
задания, запись результата и список задач; shell, сеть, MCP и доступ к FULL
или Gold не предоставлялись. Требования и контракт результата были общими.
Импортёр и оценщик не исправляли бизнес-содержание ответа OpenCode.

В новых сериях: backend `deepseek-flash`, T=`0.2`, `thinking` отключён.
На попытку: до **$2**, **512 вызовов**, **131 072 выходных токенов на ответ**,
**3600 секунд активного выполнения**. Суммарного лимита токенов не было;
стоимость контролировалась отдельно. Фактическое число вызовов различалось.

Это сравнение методов в заданных ограничениях, не всех возможностей OpenCode.
DeepSeek выбран как единый доступный по бюджету backend; его превосходство
над GPT или Claude этим опытом не проверялось.

## Полученные результаты

На двух проектах с **59 и 74 ФТ**, по одному запуску каждого метода:

- оба метода доставили пакеты без обрезаний, с полной структурной цепочкой каждого ФТ;
- Milestone F1 FULL: **0.684 / 0.636**, OpenCode: **0.519 / 0.456**;
- FULL быстрее на **25.1% / 36.9%**, но дороже на **57.3% / 20.4%**;
- Trace F1 FULL: **1.000 / 0.986**, OpenCode: **0.966 / 1.000**;
- на 74 ФТ Recall этапов и F1 ветвлений у FULL ниже: выигрыш есть не по всем метрикам.

Отдельная серия: **6 проектов, 6/10/12/19/24/48 ФТ, два метода, два повтора
= 24 попытки**. Полные принятые пакеты: FULL **9/12**, OpenCode **11/12**.
F1 этапов у FULL выше в каждой группе размера, при этом Recall ниже.
Четыре диагностических повтора не заменяют исходные отказы.

Температурный пилот на 7 и 9 ФТ завершил **16 из 24** попыток T=0/0.2/0.7.
По заранее заданному правилу при неполной сетке сохранена T=0.2.
Оптимальность не установлена. Ненулевая температура допускает вариативность,
но сама по себе не доказывает независимость повторов.

Все пять групп Precision/Recall/F1, структурные показатели, исходы и ресурсы
есть в отчёте и числовом приложении. Gold — авторский кандидат эталона.
Два проекта на группу не доказывают универсальность или причинное влияние
размера. Общего устойчивого преимущества по трассировке эти серии не устанавливают.

## Установка и безопасная демонстрация

Нужны Python 3.11+, Poetry и Git:

```bash
git clone https://github.com/ArtemBotsman/agent_langgraph_diagrams.git
cd agent_langgraph_diagrams
poetry install --with evaluation
poetry run traceable-spec \
  examples/event_signup_specification_req.json \
  artifacts/single_runs/event-signup-b0 \
  --mode B0_RULE
```

`B0_RULE` не обращается к API. Каталог результата должен быть новым или пустым.
Сохраняются `generated_specification.json`, Use Cases, stories, Mermaid,
`trace_manifest.json`, отчёты проверок и `run_manifest.json`.

Для сетевого запуска отдельно заполните `.env` по `.env.example` и явно
передайте `--allow-live`. Ключи никогда не добавляются в Git.

**Воспроизведение:** обычный CLI `--mode FULL` сохраняет прежний профиль
по умолчанию. Это не готовая команда повторения исследовательского `FULL_NEW`.
В исследовании использованы `terminal_consistency_deps(..., contract_version=V2)`
и `CacheAwareFullClient`, передающий фактическую T=0.2. Сам профиль V2
температуру не переключает. Демонстрационные параметры `.env.example`,
включая лимит 8000, не являются настройками новых серий.
Исследовательские ограничения задавались отдельными зафиксированными обёртками.

## Код и проверки

```bash
poetry run pytest -q
```

- `agents/use_case`, `agents/activity` — специализированные графы;
- `prompts/source_context.py` — полный исходный контекст;
- `orchestration/terminal_consistency.py` — исследовательский профиль;
- `evaluation/terminal_flow.py`, `contracts.py` — проверки потоков и контрактов;
- `reference_methods/` — внутренние baseline и внешний адаптер;
- `scripts/jury_stage46_client.py` — исследовательский клиент и учёт;
- `tests/` — локальные регрессионные проверки.

Числовое приложение позволяет проверить сводные расчёты, но не заменяет
полный журнал: закрытые проекты руководителя, ключи и персональные пути
не публикуются. Старый открытый синтетический benchmark в `benchmark/`
остаётся отдельным набором.
